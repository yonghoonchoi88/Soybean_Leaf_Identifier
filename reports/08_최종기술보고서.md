# 산출물 8. 최종 기술 보고서 — 콩잎 질병 분류 Vision AI 서비스

> ResNet-18을 콩잎 3클래스로 Fine-tuning하고, FastAPI 동기 API · Redis 캐시 · Celery 비동기 작업 · PostgreSQL 작업 기록을 Docker Compose로 묶어 서비스했다.
> 제공 코드 그대로의 기준선(Head-only) Validation **0.767**에서 Full Fine-tuning + 증강으로 **0.993**까지 올려 모델을 선택했고, 선택된 모델의 **최종 Test 정확도는 0.953**이다.
> 가장 위험한 오류인 **"병든 잎을 정상으로 놓침"은 Validation 11장 → 1장, 최종 Test 0장**이다. 모든 수치는 실제 실행 결과다.

## 3. 모델 결과

![모델 선택과 최종 평가](figures/val_vs_test.png)

| ID | 학습 방식 | Validation | Val 병을 놓침 | 학습 파라미터 |
|---|---|---:|---:|---|
| E0 | Head-only (필수 기준선) | 0.7669 | 11 | 분류 헤드 1,539개 |
| E2 | Full Fine-tuning | 0.9699 | 2 | 전체 |
| **E3** ⭐ | Full + 증강 | **0.9925** | **1** | 전체 |

| **최종 평가 (E3, Test 1회)** | 정확도 **0.9531** · Macro-F1 0.9534 · 병을 놓침 **0** · 정상 오경보 0 · 남은 오답 6장 모두 질병 간 혼동 |
|---|---|

- **Backbone까지 학습한 효과가 결정적이었다.** E0의 Val 오답 31장 중 16장이 두 질병 간 혼동, 11장이 질병→정상 누락이었다. ImageNet 특징을 고정한 채로는 병반의 미세한 차이를 구분하지 못했다.
- **증강 효과는 확정하지 않는다.** E3는 Val에서 E2보다 3장 더 맞혀 사전 규칙을 충족했지만, 시드 1개·1회 실행이라 향상 폭을 일반화하지 않는다.
- **Test가 Val보다 낮은 것은 예상된 결과다.** Val은 best epoch와 모델 선택에 모두 쓰여 낙관적이다 (0.9925 → 0.9531).
- Test 사용 이력(선택 후 E0·E2 참고 조회, HSV 범위 조정 시 Test 사진 일부 사용)은 [산출물 1 부록](01_FineTuning_결과보고서.md#부록-test-사용-이력-원칙-점검)에 그대로 공개했다.

## 4. 시스템 구조

![시스템 구성도](figures/architecture.png)

- 동기: 브라우저 → web → Redis 캐시(HIT면 즉시) → ResNet18 → 200
- 비동기: 브라우저 → web → `media/jobs` 저장 → PostgreSQL `queued` → Redis 브로커 → worker → 캐시 확인·추론 → `done` → 브라우저가 1초마다 조회
- web과 worker가 **같은 캐시를 공유**하고, 모델은 **각 프로세스에 따로 로드**된다.
- 평가 가이드 그림(FastAPI·Celery는 WSL)과 달리 **02 교재 22번 방식으로 4개 서비스를 모두 컨테이너로 실행**했고, 증빙은 모두 이 구조에서 수집했다. 상세: [산출물 2](02_시스템_아키텍처.md)

## 6. 성능 향상 기술 검토 (평가 가이드 6번 ①→④)

| 순서 | 기술 | 이번 프로젝트에서 한 일 | 상태 | 결과 |
|---|---|---|---|---|
| ① | 이미지 증강 | `training/finetune_aug.py`로 Train에만 적용 (E3) | **구현 · 실측** | Val +3장 → 선택, 향상 폭은 미확정 |
| ② | HSV · 마스크 | `scripts/hsv_rule_analysis.py`로 잎·병반 후보 마스크, 면적비 계산 | **분석 실행** (분류에 미적용) | 녹병과 정상의 면적비가 거의 같음 |
| ③ | Grad-CAM | `scripts/gradcam.py`로 E3 오답 7장 + E0 비교 | **분석 실행** (정확도 향상 아님) | E3는 잎을 보고도 혼동 |
| ④ | 규칙 기반 보조 판단 | Validation에서 기준 설정·효과 확인 | **오프라인 시뮬레이션** (API 미적용) | 두 규칙 모두 Val에서 효과 근거 없음 → 적용 보류 |
| — | ROI·GrabCut, Contour, ORB/SIFT, ML 융합 | — | **제안만 · 미구현** | 효과 미검증 |

> **모델 성능과 보조 규칙을 붙인 시스템 성능은 별도로 보고한다.** 아래 규칙 결과는 E3 모델의 정확도(Test 0.9531)를 바꾸지 않는다. ②③은 최종 평가가 끝난 뒤의 오답 분석이다.

### ① 이미지 증강 (구현·실측)

| 증강 | 설정 | 이유 |
|---|---|---|
| 좌우 반전 · 회전 ±20° · 밝기·대비 ±0.2 | Train에만 | 촬영 방향·조명 차이 |
| 색조(hue)·채도 | **변경 안 함** | 녹병(적갈색)과 반점병(황갈색)은 색이 핵심 단서 → 라벨과 맞지 않는 이미지 생성 위험 |

- 학습 곡선: E2는 Loss가 0.09까지 내려갔지만 Val은 epoch 1이 최고 → 학습 이미지에 맞춰지는 경향. E3는 Loss가 0.14로 덜 내려갔지만 Val이 계속 상승 → 규제 효과로 해석 (`figures/training_curves.png`).
- 결론: **Val에서 +3장으로 선택 규칙을 충족**했지만, 1회 실행이라 향상 폭은 확정하지 않는다.

### ③ Grad-CAM (분석) — 모델은 어디를 보고 틀렸나

![Grad-CAM 오답 분석](figures/gradcam/gradcam_summary.png)

- 열 구성: 원본 · E3 예측 근거 · E3의 정답 클래스 근거 · 같은 사진의 E0 예측 근거
- **E3의 근거는 오답 7장 대부분에서 잎 영역(일부 줄기·가장자리 포함)에 있었다.** 문제는 배경이 아니라 병반 특징의 구분이다.
- **같은 사진에서 E0는 7장 중 3장(`bean_rust_test.15`, `.28`, `.3`)에서 흙·배경 쪽에 근거가 있었다.** Full Fine-tuning이 "보는 곳"을 잎 쪽으로 옮긴 정황이다.
- 한계: **오답 사진만 본 관찰**이라 일반화할 수 없다. Grad-CAM은 7×7 특징 지도에서 시작해 작은 녹병 돌기 하나하나를 짚지 못한다.
- E0가 맞히고 E3가 틀린 사진도 있다 (`bean_rust_val.8`: E0 bean_rust 0.56 / E3 healthy 0.95).

### ② OpenCV HSV (분석) — 색으로 병반을 셀 수 있나

![HSV 병반 후보 분석](figures/hsv/hsv_summary.png)

처리: `cvtColor(BGR→HSV)` → 녹색 `inRange` → `Opening` → 잎 안쪽 구멍 채우기(테두리와 이어진 흙·배경 제외) → 잎 안의 갈색·황갈색 픽셀 = 병반 후보 → 면적비

| 클래스 (Validation) | n | 병반 면적비 p25 | **중앙값** | p75 | 병반 색조 중앙값 (H) |
|---|---:|---:|---:|---:|---:|
| angular_leaf_spot (반점병) | 44 | 0.0084 | **0.0154** | 0.0296 | 20 |
| bean_rust (녹병) | 45 | 0.0032 | **0.0067** | 0.0186 | 19 |
| healthy (정상) | 44 | 0.0020 | **0.0068** | 0.0148 | 20 |

- 반점병은 병반이 크고 뚜렷해 면적비가 높았지만, **녹병과 정상은 중앙값이 거의 같았다.** 녹병의 작은 돌기는 256×256 축소에서 잘 잡히지 않고, 정상 잎에서도 손·흙·잎 구멍이 병반 후보로 잡혔다.
- 색조(H) 중앙값도 세 클래스가 19~20으로 같아 **색조로 두 질병을 나눌 수 없었다.**
- E3가 healthy 0.95로 틀린 `bean_rust_val.8`은 병반 면적비 0.0014로, **모델과 색 규칙 모두 병반을 보지 못한 사례**다.
- 방법상 한계: HSV 색 범위는 소수 샘플 화면을 눈으로 보며 정했고, 그 샘플에 **Test 오답 사진 일부가 포함**되었다(누출). 그래서 HSV 결과는 참고용이며 서비스 판단에 쓰지 않는다.

### ④ 규칙 기반 보조 판단 (오프라인 시뮬레이션)

라벨을 바꾸지 않고 **"확인 필요"만 표시**하는 규칙을 Validation에서 정하고 효과를 확인했다.

| 규칙 | 조건 | 기준값 출처 |
|---|---|---|
| R1 정상 의심 | 예측이 healthy인데 병반 면적비 > **0.0249** | Val에서 healthy를 맞힌 사진의 95백분위 |
| R2 저신뢰 | 1·2위 점수 차 < **0.4** | E0 Validation margin 분석 (0.4 이상 구간 정확도 97.6%) |

| 규칙 (Validation 133장) | 보류 | 보류율 | 잡은 오답 | 보류 안 한 사진의 정확도 |
|---|---:|---:|---:|---:|
| R1 정상 의심 | 3 | 2.3% | 0 / 1 | 0.9923 |
| R2 저신뢰 | 4 | 3.0% | 0 / 1 | 0.9922 |
| R1 ∪ R2 | 7 | 5.3% | 0 / 1 | 0.9921 |

- **R1(색 규칙)은 기각한다.** 유일한 오답(`bean_rust_val.8`)은 병반 면적비가 0.0014로 낮아 잡히지 않았고, 정상 잎 3장만 보류했다.
- **R2(점수 차 규칙)는 적용을 보류한다.** E3의 Validation에는 점수 차가 작은 오답이 없어(유일한 오답의 점수 차 0.90) 효과를 확인할 근거가 없다. 기준 0.4도 E0 분석에서 가져온 값이다.
- **확신을 갖고 틀린 사례는 어떤 규칙으로도 잡지 못한다.** 점수와 독립적인 새 근거가 필요하다.
- 이 규칙을 Test에도 적용해 본 결과(R2: 보류 3.9%, 오답 4/6 포착)가 있지만, Test는 이미 여러 번 조회된 상태이고 R1은 HSV 범위 조정에 Test 사진을 본 누출이 있어 **참고값으로만** [산출물 1 부록](01_FineTuning_결과보고서.md#부록-test-사용-이력-원칙-점검)에 둔다. R2의 효과는 **새 데이터로 다시 검증**해야 한다.
- 원본: `reports/data/hsv_rule_summary.json`, `hsv_features_val.csv`

### 제안만 한 기술 (미구현 · 효과 미검증)

| 기술 | 아이디어 | 이번 분석에서 얻은 근거 | 확인 방법 |

| CNN + ML 융합 | CNN 점수 + HSV·Contour 특징 → RandomForest 보조 분류 | 현재 HSV 특징은 녹병·정상 구분력이 낮음 | Train 내부 교차검증으로 특징 생성 |

| 비동기 MISS | **9.12 ms** (접수, −56.8%) | 116.35 ms | 20.34 ms |
| 비동기 HIT | 10.11 ms (접수) | 127.64 ms | 생략 |

- 비동기는 접수가 빠를 뿐 결과 확인은 동기보다 95ms 느리다 (조회 간격 0.1초 영향). **추론이 빨라진 것이 아니다.**
- 첫 요청(cold)은 모델 로딩 때문에 2.2~3.0초. 워밍업은 비교에서 제외했다.
- Redis 장애 시 동기 응답 8.06초, 비동기 503까지 20.67초 (Docker DNS 이름 조회 실패).

## 10. 한계

1. **데이터:** 단일 출처(Makerere beans), Test 128장(1장 = 0.78%p). 다른 지역·카메라·조명의 현장 사진에서는 미검증.
2. **실험:** 각 실험 시드 1개 1회 실행. 증강 효과는 불확실.
3. **모델 판단:** score는 보정된 확률이 아니며, 확신 오답(0.95)이 존재한다. "콩잎이 아님"을 판단하지 못한다.
4. **시스템:** 동시 요청 부하는 측정하지 않았다. worker는 solo·1개라 작업이 몰리면 순서대로 처리된다.
5. **실행 방식:** 평가 가이드의 WSL 실행 방식으로는 02 통합을 검증하지 않았다.
6. **Test 사용:** 선택 확정 후 E0·E2도 Test로 참고 조회했고, HSV 색 범위 조정에 Test 사진 일부를 봤다. 최종 성능 보고는 E3 1회 결과만 쓰며, 이 Test 세트는 이후 개선 검증에 다시 쓰지 않는다.

## 부록 B. 예상 질문과 답

| 질문 | 답 (근거) |
|---|---|
| Val 0.993인데 Test는 0.953이에요. 과적합 아닌가요? | Val은 best epoch와 모델 선택에 두 번 쓰여 낙관적인 값입니다. 그래서 일반화 성능은 한 번도 안 본 Test 0.953으로 보고했습니다. E3의 train loss(0.14)가 E2(0.09)보다 높아 학습 데이터를 외운 쪽은 오히려 E2입니다. |
| Test는 정말 한 번만 썼나요? | 모델 선택은 Test를 보기 전에 Validation 규칙으로 확정했고, 최종 성능은 E3의 Test 1회 결과입니다. 다만 선택 후 E0·E2도 참고로 Test를 조회했고, HSV 색 범위를 정할 때 Test 사진 일부를 봤습니다. 이 이력은 산출물 1 부록에 그대로 공개했고, 이 Test 세트는 이후 개선 검증에 쓰지 않을 계획입니다. |
| 증강을 넣은 E3를 왜 골랐나요? | 실험 전에 "Val에서 2장 이상 더 맞히면 E3"라는 규칙을 정했고 E3가 3장 더 맞혔습니다. 다만 1회 실행이라 증강의 효과 크기는 주장하지 않습니다. E3는 Test에서 healthy를 오류 없이 구분했습니다. |
| Head-only가 왜 그렇게 낮았나요? | 학습되는 파라미터가 분류 헤드 1,539개뿐이라 ImageNet 특징을 그대로 씁니다. 두 질병의 반점 차이를 표현하지 못해 질병 간 혼동이 20장이었습니다. Grad-CAM에서도 E0는 배경을 보는 사례가 있었습니다. |
| 비동기가 더 느린데 왜 쓰나요? | 비동기의 목적은 추론 가속이 아니라 접수와 처리 분리입니다. 웹 서버는 9ms 만에 응답하고, 무거운 작업이나 요청이 몰려도 웹이 묶이지 않습니다. worker를 꺼도 작업이 큐에 남아 재시작 후 처리되는 것을 확인했습니다. |
| 캐시 키에 왜 모델 경로를 넣었나요? | 모델을 바꿨을 때 이전 모델의 결과가 섞이지 않게 하기 위해서입니다. 실제로 E0 → E3 교체 후 같은 이미지가 새 키로 처리되었습니다. |
| Redis가 죽으면 어떻게 되나요? | 동기는 캐시 없이 추론해서 200을 주고, 비동기는 503과 함께 DB에 `failed`를 남깁니다. 직접 Redis를 꺼서 확인했고, 응답이 8초·20초로 늦어지는 문제를 찾아 서킷 브레이커를 제안했습니다. |
| 점수 0.95로 틀린 건 어떻게 막나요? | 점수 기반 규칙으로는 막을 수 없습니다. 색 면적비 규칙도 Validation에서 효과가 없어 기각했습니다. 고해상도 입력과 데이터 보강이 다음 단계입니다. |
| 제공 코드를 수정했나요? | 수정하지 않았습니다. 증강은 제공 `finetune.py`를 재사용하는 래퍼로 구현했고, 평가·측정·분석은 별도 스크립트 6개로 추가했습니다. |
| 학습은 GPU, 서비스는 CPU인 이유는요? | 학습은 WSL의 RTX 3060에서 했고, 서비스 컨테이너는 CPU 전용 torch로 구성되어 있습니다. ResNet-18은 CPU에서도 warm 추론 약 16~20ms라 서비스에 충분했습니다. |
| 콩잎이 아닌 사진을 넣으면요? | 3클래스 중 하나로 답합니다. 고양이 사진이 bean_rust 0.525로 나왔고, 실제 병든 잎보다 점수가 높았습니다. 그래서 점수로는 거를 수 없고, 별도 입력 검증이 필요하다고 판단했습니다. |
